## Verification order

`verifyNativeToken` / `verify_native_token`: bounded canonical decode → genesis data/reason present
→ deployment from the allow-list → compact-history relation (profile, deadlines, strict unlocks,
lock digest) → offline lock proof → per-leaf bridge checks (fixed-profile guards, aggregator
admission, path budget, `t ≤ IR.timestamp`) → **the SDK's own ordinary verification with the same
trust base** and this bridge's justification/issuance registrations. Nothing in these paths has a
network capability (source scan + a sandboxed no-network run in both suites).

## Fixed-base profile (design v2)

One pinned SDK `RootTrustBase`: unit weights, one epoch, SDK count quorum `N − (N−1)/3`.
`trustBaseId = SHA256(B)` of the exact SDK JSON document bytes; `TrustInput::from_json` /
`TrustInput.fromJson` hash the installed bytes. Epoch changes, appended records, fetching newer
bases and arbitrary weights are **DEFERRED** to the common SDK work (ristik/bft-core#421); weighted
and rotating scenarios are `#[ignore]` / skipped placeholders, not passing coverage. Known
SDK/native limitations (TS binds seal recovery parity, Rust does not; B1 accepts 64-byte seals) are
not papered over here.

## Reconciliation with PR1 (`protocol/`)

Rebased on `pr1/protocol`. Manifests follow `protocol/manifest.schema.json` (a registry object keyed
by `tokenTypeHex`; `trustBase.document.sha256` is the single trust pin). Installation recomputes
identifiers, `chainRef`, Cfg/cfg and policy hashes and cross-checks installer-supplied artifacts
(`pdr`, `executionProfile`) against their pins. Choices that `protocol/` does not yet fix are
isolated and should be confirmed by PR1/PR2:

1. **`evmBackingPolicy.configurationHash`** is read as the genesis `ConfigHash` of the EVM partition
   description: `SHA256(tag(39008, array15))` with elements 12..14 replaced by
   `0, 0, null`, matching native `evmassign.ConfigHash`. The full UC configuration commitment
   hashes the tagged, unmodified record. `tests/interop/native-pdr.go` produces the independent
   native-codec fixture; both SDK constructor suites reproduce its bytes and hashes.
2. **Execution profile artifact** (`evmBackingPolicy.executionProfile`) is, for now, the UTF-8 JSON
   `{"headerFields":20|21}` selecting the Cancun or Prague header shape.
3. **Fixtures** in `tests/interop/fixtures.json` are provisional cross-stack fixtures generated by
   the TS constructors (`scripts/gen-fixtures.ts`) and replayed by Rust, which also rebuilds the
   positives byte for byte. They are not the normative corpus (`protocol/vectors` awaits PR2).
4. The kernel result ABI (`448+128m`) and B1 calls are out of scope here (ureth/contracts).

## Burn handoff and request binding

Construct `NativeBridgePayments` with an explicit journal. `MemoryRedemptionJournal` is a
volatile test/demo choice. `burnForReturn` and `recoverPendingBurns` both require a `persist`
callback that stores the complete certified blob durably before resolving. A failed write leaves
the wallet burn unacknowledged and recoverable. A fresh adapter can read the handoff independently
of its in-memory journal; acknowledgement records handoff, not vault payment.

Both stacks expose `verifyBurnRequestBytes` / `verify_burn_request_bytes`. They verify the held
receipt and returned burn, require exactly one appended burn, preserve the exact genesis and all
prior transactions/CD/reference times, and match the requested reason bytes. Proof refresh under
the same installed base is allowed. The TS adapter runs this check before persistence or acknowledgement.

Full-token scans run before SDK byte decoding and also gate decoded-token verification and
refresh. Nested J/PDR/UC/value/reason/predicate-code CBOR shares the outer depth/item budget. Every ordinary and
embedded UC has the 16 KiB limit, native summary/shard/path/signature/node-ID sublimits and the
supported 65-byte signature encoding. Embedded UC, ordinary UC-tree paths and RSMT paths share
one cumulative 2048-step budget. The independent constructor fixtures are separate from the released Go corpus;
corpus integrity/regeneration and joined component CI check their respective boundaries.

## Host readiness contract for return proofs

Protocol 4 has no certificate-age window: B1 accepts an anchor of seal round `r` when `r` lies in the permanent registry entry of the anchor's
own epoch (`start <= r <= O`, and `r < end` for a closed epoch), `O` being the registry `clock.rootRound` at the redemption's execution block (not
the shard round, `t` or a wall clock). An old certificate never expires; a new one can be ahead of the registry. The executing block imports its
own origin, so a read of the latest block is advisory: the host sends only when `max(r) <= O`. There is no `W_cert`, no execution margin and no
spread rule, and the plug-in does not require the anchors to be close in round or epoch.

`buildReadyReturnProof` and `redeemReturn` (TypeScript; `readiness::classify_readiness` in Rust) refetch every leaf for the SAME burned token
(never rebuilding or re-burning, never to obtain matching certificates or fewer anchors), wait a bounded time for an origin that has not imported
the newest anchor, and send within a bounded number of attempts. An exhausted wait or temporary witness unavailability is `ErrProofUnavailable`
with a diagnostic cause (the unavailable family, retryable, pending state kept); an over-limit anchor count, gas or size stays BudgetExceeded and
is never retried. Before any resend the host checks the transaction's receipt and the
vault's spent/credit state: an RPC timeout is not a revert, an unknown send is not repeated while it may be pending (`RedemptionUnconfirmed` carries the
transaction hash; the caller passes it back as `pending` and its receipt is checked before any new send), and the wallet burn is never
repeated. A revert is retried up to `maxSends` whatever its cause, so a deterministic refusal (a closed authority interval, bad backing) costs
`maxSends` transactions. A proof service or chain reader that fails is retried within the attempt bound and reported as `ErrProofUnavailable` with
the cause; the policy is range-checked before anything is fetched. The burn-time preflight is a feasibility filter, not a service guarantee: it
prices the best case with ONE anchor, because a single certificate may serve every leaf; it never projects one anchor per shard. The burn is therefore refused only when even that best case cannot pass the gate; a bundle fetched later
can still fail the gate (`ErrGasBudget`, "direct exit unavailable", not "token invalid").

### The anchor table

The aggregator policy names the partition only. Each anchor is read from its own UC (its shard, shard configuration hash and partition); the
plug-in routes a leaf to an aggregator by its state ID, and whatever certificate the response carries is kept with its path. The depth of an anchor is
the depth of its own shard ID, and every leaf's state ID must carry the prefix bits of the anchor it names. Parent and child shards of a topology
split may both appear in one history. The gate is `21000 + 16*D_max + 80*B_env + 1000*J + G_kernel + G_batch + sum G_leaf + 1,000,000`, with `J`
the CBOR item occurrences of the Cfg, the policy, every UC and every IR opening (at most 4,096) and `G_batch` the price of the one
`CERT_BATCH_V2` call, grouped by `certgroups.ts` / `certgroups.rs` exactly as the contract and the oracle do.

## From burn to claimed native funds (wallet lifecycle)

The journal entry (`RedemptionEntry`) moves `burned` -> `submitted` -> `redeemed` -> `settled` and every step is written by the plug-in
(`redeemBurned`, `claimCredited` in `lifecycle.ts`), never inferred from the wallet burn acknowledgement:

- `redeemReturn` asks the vault, before any proof is fetched or the origin is read, whether the token's lock nonce is already credited, so an
  already executed redemption (a third party's, or an earlier send whose hash was lost) is reported as such even while the proof service is down.
  This holds with pending hashes too: a hash whose receipt is a success ends the call, a hash with no receipt is believed only when the vault does not
  show the nonce credited (a dropped transaction never gets a receipt). The
  vault keys spent state by the lock **nonce**, not the nullifier: `RedeemTransport.spentNullifier(nonce)` returns the burn nullifier the vault stored
  (`spentNullifier(uint256)`; the nullifier is also an indexed topic of `RedemptionCredited`). A nonce credited to a different burn is `ErrUnexpectedBurn`.
- The entry is `submitted` before each send and keeps every sent hash (`redeemTxs`); an unconfirmed send leaves it `submitted`, and a restart passes the
  hashes back so their receipts are checked before any resend. The entry is `redeemed` once the vault credited `releaseTo`.
- `claimCredited` claims the entry's amount to `to` (an amount that does not fit a word, the zero address and the vault itself are refused before any gas is
  paid), journals the claim hash, waits for its receipt and reads `claimable(releaseTo)`: the entry is `settled` only when the receipt succeeded AND the
  balance fell by exactly the claimed amount (a claim resumed from its journalled hash settles on its receipt alone: the balance before is gone). The attempt is
  journalled before the send; one without a recorded hash (a crash in between) is never repeated automatically, because a second claim would take the same
  recipient's other credit. A reverted claim leaves the entry `redeemed`; an unconfirmed one keeps its hash and is checked before any resend.
- A send that is dropped and never mined blocks its entry; there is no inference. The host procedure: establish from its own evidence that the transaction is
  dead (the sender's nonce was used by another transaction, or it was replaced) and call `abandonAttempt` (a redeem hash, or the claim attempt); the entry then
  sends again. Wrongly abandoning a pending claim can pay twice, so this is the host's decision, not the plug-in's. The redeem side also recovers by itself once
  anyone redeems the nonce.
- A bundle over the anchor, gas or size bound is a budget refusal and is not retried; the refusal carries the measured distinct-anchor count (for the anchor ceiling
  itself, "N distinct anchors fetched, ceiling 8").
  Without a proof source a held token that does not verify is reported as the failure it is, not as an unavailable service.
